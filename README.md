# Who Made This?

An orphan AWS resource archaeologist with a reversible **Purgatory** state.

Every quarter somebody has to open the AWS console and answer a question nobody
can answer: is this still needed? There is a stopped instance from March, an
unattached volume, three Elastic IPs pointing at nothing, and no `Owner` tag on
any of them. The person who created them may not work here any more. So the
resources stay, because deleting something you cannot explain feels worse than
paying for it.

That instinct is correct. The annoying task is not the cleanup, it is the
archaeology.

This runs weekly, works out **who created each resource and when** from
CloudTrail, scores how likely it is to be abandoned, and emails a digest with
two links per resource: **Keep** or **Send to Purgatory**.

## Purgatory

A reversible middle state. A resource sent to Purgatory is:

- stopped (instances) or snapshotted (volumes)
- tagged `whomadethis:release-after` with a date 30 days out
- listed in every digest until then, with a one-click restore

After 30 days with nobody claiming it, the app emails you a list and says these
look safe to delete now. Then you delete them.

**The app cannot delete anything.** Not "will not". Cannot. There is no
`Delete*` and no `Terminate*` action in any IAM policy in `template.yaml`. That
is the security model, and it is enforced rather than promised.

## The Orphan Score

Deterministic, out of 100, and the email shows the arithmetic. Same account
state always produces the same number.

| Signal | Points |
|---|---|
| No `Owner` / `owner` / `CreatedBy` / `team` / `contact` tag | 25 |
| **Cold attribution:** no CloudTrail event in 90 days | 25 |
| Idle shape: stopped instance, unattached volume, unassociated EIP or ENI | 20 |
| No IaC provenance: no CloudFormation tag, creator is not a cfn/terraform/cdk role | 15 |
| Creating IAM identity no longer exists | 15 |

- below 40: informational only
- 40 to 59: flagged, asks for a Keep confirmation
- 60 and above: Purgatory candidate. Ignoring the email for 7 days sends it there.

There is no LLM in the scoring path, or anywhere else. The summary paragraph is
generated by `summarise()` in plain Python so the output is auditable and
reproducible.

### Why CloudTrail Event history and not CloudTrail Lake

Lake ingestion costs $0.75/GB on one-year extendable retention with no free
tier, and more importantly an event data store only captures events **from the
moment you create it**. There is no history to be an archaeologist about.

CloudTrail Event history is on by default in every account, holds the last 90
days of management events, is queryable through `LookupEvents`, and there is no
charge for viewing it. So attribution works retroactively the minute you deploy.

The 90 day boundary then becomes the best signal in the app. If a resource
exists and CloudTrail has no record of anything touching it in 90 days, that
silence is stronger evidence of abandonment than any known creator. Hence
**cold attribution**, weighted the same as a missing owner tag.

## Architecture

```
EventBridge Scheduler  (weekly cron, Fri 18:00 IST)
        |
        v
  scanner Lambda ── EC2 Describe APIs (read-only inventory)
        |         └─ CloudTrail LookupEvents (attribution, 90 days, free)
        |            → Orphan Score (deterministic Python)
        v
   DynamoDB  (state: INFO | FLAGGED | KEEP | PURGATORY | RELEASABLE)
        |
        v
   Amazon SES  →  digest email with HMAC-signed Keep / Purgatory links
                        |
                        v
              decide Lambda (Function URL, AuthType NONE)
                verifies HMAC-SHA256 signature + expiry
                        |
              ┌─────────┴──────────┐
             KEEP              PURGATORY
        skip forever      stop + snapshot + tag

EventBridge Scheduler (daily) → enforcer Lambda
   grace expired with no reply → Purgatory
   Purgatory term complete     → RELEASABLE report (human deletes)
```

**Authentication.** The decision links act on an AWS account with no login, so
the link itself is the credential: each URL carries the resource id, the action,
an expiry, and an HMAC-SHA256 signature over all three. The signing key lives in
SSM Parameter Store as a SecureString (free for standard parameters, unlike
Secrets Manager at $0.40/secret/month). Change one character of the signature
and you get a 403.

## Services used

AWS Lambda, Amazon DynamoDB, Amazon SES, Amazon EventBridge Scheduler,
AWS CloudTrail, Amazon EC2, AWS Systems Manager Parameter Store, AWS SAM.

## Cost

Well under $1. Lambda, DynamoDB and EventBridge Scheduler usage all sit inside
their free tiers, and CloudTrail Event history is free to query. The only real
line item is SES at $0.10 per 1,000 messages, and the app sends about eight a
month. Deliberately avoided: CloudTrail Lake, Secrets Manager, API Gateway,
NAT Gateway, anything in a VPC.

## Deploy

Prerequisites: AWS CLI, [AWS SAM CLI](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/install-sam-cli.html),
Python 3.12, and an SES-verified email address.

```bash
chmod +x *.sh

# 1. Give the scanner something to find (optional, but an empty account
#    produces an empty email). Wait ~15 min for CloudTrail to catch up.
./seed-orphans.sh us-east-1

# 2. Verify SES, store the signing key, build, deploy, and run one scan.
./run.sh you@example.com us-east-1
```

`run.sh` exits early with instructions if your address is not SES-verified yet.
A new SES account is in the sandbox, so **both** sender and recipient must be
verified. Emailing yourself is fine.

Check your inbox, then click **Send to Purgatory** on the seeded volume and
confirm the snapshot:

```bash
source .seeded-resources
aws ec2 describe-snapshots --owner-ids self --region "$REGION" \
  --filters "Name=tag:whomadethis:source,Values=$VOL" \
  --query 'Snapshots[].[SnapshotId,State,Description]' --output table

aws ec2 describe-tags --region "$REGION" \
  --filters "Name=resource-id,Values=$VOL" --output table
```

Then click **Keep** on the same resource to prove the reversal works.

To prove the signature guard, edit one character of `sig` in any link. You
should get a 403 page.

## Teardown

```bash
./teardown.sh us-east-1
```

Removes the seeded instance and volume, their Purgatory snapshots, the stack,
and the signing key.

## Known limitations

- **90 day attribution window.** Anything older comes back unattributed. Scored
  as a signal, but it is a real gap.
- **Single region, single account.** `LookupEvents` is per-region. No AWS
  Organizations sweep.
- **Four resource types.** No RDS, S3, Lambda or load balancers, which is where
  most of the real spend hides.
- **`LookupEvents` throttles at roughly 2 requests/second.** The 0.6s pace makes
  a 200-resource scan take about two minutes. Fine weekly, wrong at enterprise
  scale.
- **Filtered DynamoDB scans.** Correct at this size, wrong at scale. A GSI on
  `state` is the fix.
- **Elastic IPs and ENIs are flagged but never modified.** Releasing an EIP is
  not reversible and you may not get the same address back, so this app refuses
  to touch them.
